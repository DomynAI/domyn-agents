Events and streaming

A turn of an agent is a stream of events. The Runner executes the agent and yields an event for each step: the agent starting, each model call, each tool call and its result, each hand-off in a team, and the reply. An interface that shows an agent to a user — a web app, a chat bot, the interactive CLI — is a loop over these events.

This page shows how to read that stream. Event types lists every type with its fields.

Running a turn​

import asyncio

from domyn.agents import BaseEvent, ExecutionEventType, Part
from domyn.agents import Runner

runner = Runner()


async def ask(agent, text: str, conversation_id: str | None = None) -> str | None:
    user_input = BaseEvent(
        event_type=ExecutionEventType.USER_INPUT,
        author="user",
        content=[Part(text=text)],
    )
    async for event in runner.run(
        application_name="weather-app",
        user_id="user-42",
        root=agent,
        user_input=user_input,
        conversation_id=conversation_id,
    ):
        conversation_id = event.conversation_id
        match event.event_type:
            case ExecutionEventType.TOOL_START:
                print(f"[{event.author} calls {event.action.name}: {event.action.thought}]")
            case ExecutionEventType.RESPONSE_TOKEN | ExecutionEventType.RESPONSE:
                print("".join(p.text or "" for p in event.content), end="", flush=True)
    print()
    return conversation_id
ArgumentDescription
application_nameName of your application. Conversations are stored per application.
user_idWho is talking. Approval grants and stored conversations are kept per user.
rootThe agent the user talks to. In a team, the main agent.
user_inputThe message, as a USER_INPUT event.
conversation_idThe conversation to continue. Without one, the runner starts a new conversation and every event of the turn carries its id: pass it back on the next turn to continue.

What a turn looks like​

An agent with one tool, asked about the weather, produces these events:

event_typeauthorWhat it carries
agent_startAssistantThe user's message, as content and as the task in action.parameters
llm_startAssistant
llm_endAssistant
tool_startAssistantaction: get_weather, parameters={'city': 'Rome', 'reasoning': 'Need the weather.'}, thought='Need the weather.'
tool_endAssistantThe same action, with observation='Sunny in Rome'
llm_startAssistant
llm_endAssistant
responseAssistantcontent: It is sunny in Rome.
agent_endAssistant

With the default tool_use_thought planner, action.parameters also holds the reasoning argument the planner adds to each call, the same text as action.thought.

The user's own message is not yielded: the stream starts with agent_start. The turn ends with the root agent's agent_end, or earlier when it pauses for approval, fails, or a hook stops it, in which case the last event is the hook's response.

The event​

Every event is a BaseEvent. The fields an interface uses:

FieldDescription
event_typeWhat happened, an ExecutionEventType.
authorThe agent the event belongs to. In a team, this is how events of different agents are told apart.
contentA list of Parts. A part's text is meant for the user; its thought is the agent's reasoning.
actionFor tool and agent events, the call: name, parameters, thought (why the model made it), call_id, and on tool_end the observation, the result the model reads.
is_partialTrue for a piece of a longer output that more pieces will follow.
error_code, error_messageSet on errors.
metadataExtra data, depending on the type: token counts on llm_start, the approval subject on tool_needs_feedback.
conversation_id, turn_id, interaction_id, event_id, timestampIdentifiers, for storing or correlating events.

Showing a turn to a user​

Most interfaces handle a handful of types and ignore the rest:

ShowEvents
The replyresponse_token while it streams; response when it does not stream, and for text a tool streams (is_partial)
That the agent is workingllm_start and llm_end
Tool callstool_start (with action.thought), then tool_end with the result, or tool_error
Progress of a long tooltool_update (see streaming tools)
Hand-offs in a teamagent_call, then the other agent's events, ending with its agent_end
A request for approvaltool_needs_feedback
A failureerror_occurred

Rendering both response_token and response never shows a reply twice: a streamed reply is not repeated as a response.

Streaming​

Agent.stream decides how the reply arrives. It is False by default; the interactive CLI turns it on.

  • stream=False: the reply is one response event.
  • stream=True: the reply arrives as response_token events, each carrying the next piece in content, as the model produces it. No response follows.

So an interface that only handles response shows nothing for a streaming agent. Handle both.

With streaming on, response is still emitted for replies that were not streamed:

  • a reply the agent forwards unchanged from a tool or a team member (FORWARD_VERBATIM, see Orchestration), marked with forward_verbatim in metadata;
  • the message of a hook that stops the turn (see Hooks);
  • a reply that asks the user a question and waits for the answer (need_feedback set on the event).

A provider streams only if it implements generate_streaming, which all built-in providers do.

Teams​

When the main agent hands off, the stream shows agent_call from the main agent (with the task in action.parameters and the reason in action.thought), then agent_start and the events of the team member, with its name as author. Its answer arrives as its agent_end, with the answer in content, and the main agent continues.

A team member's answer is never streamed and never a response, even when its stream is on: it is addressed to the main agent, not to the user. What the user should read is the main agent's reply.

Pausing for approval​

A tool that needs a person's approval stops the turn: the stream yields tool_start, then tool_needs_feedback, and ends. The action of that event is the pending call, and metadata["approval_subject"] describes what is being approved.

To answer, run the next turn with a TOOL_FEEDBACK event instead of a user message, carrying the action of the tool_needs_feedback event (pending below) with approve set:

feedback = BaseEvent(
    event_type=ExecutionEventType.TOOL_FEEDBACK,
    author="user",
    action=pending.action.model_copy(update={"approve": True}),
)
async for event in runner.run(..., user_input=feedback, conversation_id=conversation_id):
    ...

The stream continues from tool_end: with the tool's result when approved, or with a refusal as the result when not, which the model reads and answers. Tool approvals covers who is asked, and how a grant can last beyond one call.

Errors​

EventMeaningThe turn
tool_errorA tool raised. error_code is the exception type, and the message is the result the model reads.Continues: the model sees the error and decides what to do.
hook_errorA hook raised, or returned something its phase does not accept. error_code is the exception type.For an agent or event hook: stops, with a generic message as a response, unless the hook was declared with break_on_error=False. For a tool hook: continues, and the call runs as if the hook had not. See Hooks.
error_occurredThe agent could not continue, for example because the model's API failed. error_message says why.Ends: it is the last event.

Compaction​

When a conversation approaches the model's context window, or the provider rejects a request as too long, the agent shortens it before calling the model, and the stream shows context_compaction_start and context_compacted around it, with token counts in metadata. An interface can show them to explain a pause, and why the agent may no longer remember details from early in the conversation. See Context compaction.
